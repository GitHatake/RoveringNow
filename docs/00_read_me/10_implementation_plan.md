## Phase 1：詳細設計

**ブランチ：`docs/detailed-design`**

基本設計書が「何を作るか」を定義したのに対し、本フェーズでは「どう作るか」を定義する。

- [ ] 技術スタックの選定
  - [ ] **提供形態の最終判断**（WEBアプリのままか、ネイティブアプリ化するか）
  - [ ] フロントエンド／バックエンド／データベース／インフラ
  - [ ] プッシュ通知の実現方式
- [ ] データベース設計（論理・物理）
  - [ ] **グループツリーの再帰取得**（配下配信の対象決定）
  - [ ] **グループ名の一意性制約**（同時作成時の競合を含む）
- [ ] API仕様
- [ ] 画面詳細設計・UIデザイン
  - [ ] 認証バッジの視覚表現（色以外でも判別できること）
- [ ] 認証・認可の方式
- [ ] **QR不正取得への対策方式**（動的QR・有効期限等）
- [ ] **グループのアーカイブ処理**（期限到来の検知と状態遷移）
- [ ] 監査ログの保持期間（匿名性ポリシーの実装方針）
- [ ] 認証の判断基準（運用ガイドライン）
- [ ] **ローバーポートからの新着検知方式**の調査（Phase 2向け）

### 特に判断が重い項目

**提供形態の最終判断。** 基本設計書 第14.2節の制約1のとおり、WEBアプリでは iOS でホーム画面に追加されない限りプッシュ通知が届かない。通知が生命線である本アプリにとって、この制約を受け入れるかどうかは全体の技術選定を左右する。

**配下配信の性能。** 上位グループから多数の配下グループへ配信する場合、対象メンバーの決定に再帰的な探索が必要になる。投稿操作を待たせない実現方式を設計する。
